# active directory's directory-services data model: a loving autopsy

> raw research report, 2026-10-20. one of five inputs to `../README.md`.

## 1. the schema itself

**object classes.** everything is an object; every object has an `objectClass` chain and an `objectCategory`. `user` inherits `top → person → organizationalPerson → user` (governsID 1.2.840.113556.1.5.9), with `securityPrincipal` and `mailRecipient` bolted on as *auxiliary* classes — which is how a user gets `objectSid`/`sAMAccountName` without those living on `person` ([Microsoft Learn: User class](https://learn.microsoft.com/en-us/windows/win32/adschema/c-user)). `group` is `top → group` with `securityPrincipal` auxiliary. `organizationalUnit` and `container` are both structural containers; the containment rules are expressed as `possSuperiors` on the *child* class (an OU can be created under `domainDNS` or `organizationalUnit` but not under `container` by default) and `possibleInferiors` is a constructed attribute computed from those ([Containers and Leaves](https://learn.microsoft.com/en-us/windows/win32/ad/containers-and-leaves)). the important design fact: the schema is a single, forest-wide, extensible thing — you add a class or attribute once and every DC knows it. that's a genuinely good property and one most "modern" IdPs replaced with "custom attributes: json blob."

**linked attributes.** this is the crown jewel. `member` is a *forward link* (linkID 2); `memberOf` is its *back link* (linkID 3). the spec is precise: back-link linkID = forward linkID + 1; even = forward, odd = back; a forward link can exist without a back link but not vice versa; back links are constructed and *not replicated* — each DC computes them from the forward links it holds ([MS-ADTS glossary](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/b645c125-a7da-4097-84a1-2fa7cea07714), [MS-ADTS 3.1.1.2.3](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/cf133d47-b358-4add-81d3-15ea1cff9cd9), [Win32: Linked Attributes](https://learn.microsoft.com/en-us/windows/win32/ad/linked-attributes)). other pairs: `manager`/`directReports` (42/43), `owner`/`ownerBL`. trying to write `memberOf` directly fails because "the attribute is owned by the SAM" ([Netwrix](https://blog.netwrix.com/2023/02/17/active-directory-linked-attributes/)). since 2003 forest level, link-value replication (LVR) replicates individual link values — add one member to a 1000-member group and one DN crosses the wire, not 1001.

**implications of memberOf being a back-link, not storage:**
- it's *authoritative on the DC you asked*, but only for forward links that DC holds. a global catalog (port 3268) holds other domains' objects with only the partial attribute set, and `member` is in the PAS only for universal groups. so `memberOf` "will only include Domain Local groups from the same domain of the server you are retrieving results from," omits global groups from other domains, and omits groups in external trusted domains entirely ([gabescode: what makes a member](https://www.gabescode.com/active-directory/2018/06/07/what-makes-a-member.html), [SpecterOps: group scoping](https://specterops.io/blog/2017/06/20/a-pentesters-guide-to-group-scoping/)).
- it doesn't expand nesting. direct edges only.
- it doesn't include the primary group.

**primaryGroupID.** every user has a required primary group stored as a RID integer (`primaryGroupID`, default 513 = Domain Users), matched to the group's `primaryGroupToken`. the spec says it outright: `memberOf` lists groups "except for a user object's primary group" and "a group object's member attribute will not list the user objects whose primaryGroupID is set to the group" ([MS-ADA2 memberOf](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-ada2/cc24555b-61c7-49a2-9748-167b8ce5a512), [MS-ADA3 primaryGroupID](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-ada3/e12954a4-6865-4432-94e6-00c310ca87c0)). why? windows 2000's non-LVR replication capped a multi-valued attribute at ~5000 values, and NT4 domains being upgraded had >5000 users all in Domain Users. so Microsoft stuffed the one giant membership into an integer on the user instead ([pkisolutions KB275523 mirror](https://mskb.pkisolutions.com/kb/275523)). the limit went away in 2003; the hack never did. real consequences today: Entra Connect "does not query the PrimaryGroupID attribute to build the group membership of a user" ([Microsoft troubleshoot](https://learn.microsoft.com/en-us/troubleshoot/azure/entra/entra-id/user-prov-sync/exclude-user-primary-group)). a 26-year-old replication workaround is still silently breaking cloud sync. **this is the single best cautionary tale in the whole model: a second membership encoding, introduced for a performance reason, became a permanent correctness trap for every consumer.**

**objectSid / sIDHistory.** a SID is `S-1-5-21-<96-bit random domain id>-<RID>`; the domain part is minted at domain creation, the RID allocated from a pool ([MS-AZOD SIDs](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-azod/ecc7dfba-77e1-4e03-ab99-114b349c7164), [MS-DTYP well-known SIDs](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/81d92bba-d22b-4a8c-908a-554ab29148ab)). SIDs are immutable, never reused after deletion, and all authorization — every ACL on every file, every PAC — refers to the SID, not the name ([Security Identifiers](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-identifiers)). `sIDHistory` is a multi-valued attribute of *former* SIDs; when you migrate an account between domains, the old SID rides along in the PAC so ACLs in the old domain keep working. trusts filter it by default (SID filtering / quarantine) because an attacker who can write sIDHistory can write Enterprise Admins' SID into it ([SID filtering guide](https://www.windows-active-directory.com/sid-filtering-in-complex-ad-layouts.html)).

**tokenGroups.** a constructed (operational) attribute, syntax SID, requested explicitly on a base-scope read: "the list of SIDs due to a transitive group membership expansion operation" — security-enabled groups only, includes primary group, includes nesting, requires a GC to be reachable ([MS-ADA3 tokenGroups](https://learn.microsoft.com/fr-fr/openspecs/windows_protocols/ms-ada3/1367fdb9-2098-44c1-9e75-f65ff3236539), [rlmueller](https://www.rlmueller.net/TokenGroups.htm)). it is literally "what would be in this user's access token," computed server-side. siblings: `tokenGroupsGlobalAndUniversal` (what the GC alone can answer — no domain-locals), and since 2012 `msDS-memberTransitive`/`msDS-memberOfTransitive` (DN-valued transitive closures; [MS-ADTS constructed attributes](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/a3aff238-5f0e-4eec-8598-0a59c30ecd56)).

**the global catalog and PAS.** a GC is a DC that also holds a read-only partial replica of every other domain's NC containing only attributes flagged `isMemberOfPartialAttributeSet`. "when we say a universal group is stored in the GC what we are really saying is... a group which has its `member` attribute in the PAS" — for a global group viewed via the GC, `member` is simply missing ([Morgan Simonsen](https://morgansimonsen.com/2012/02/13/exploring-the-global-catalog-and-examining-the-universalness-of-universal-groups/)). that one sentence explains the entire group-scope system.

## 2. OUs vs containers vs groups

**why containers exist at all:** backwards compatibility and system plumbing. `CN=Users`, `CN=Computers`, `CN=System` are `container` objects. "there is nothing you can do with a container that you can't do with an OU, but the reverse is certainly not the case" — the big one being you can't link a GPO to a container ([AD Cookbook ch.5](https://www.oreilly.com/library/view/active-directory-cookbook/0596004648/ch05.html)). every modern guide says don't put real objects in the default containers.

**the doctrine.** Microsoft's own planning doc: design the OU hierarchy "primarily to enable delegation of administration and control of policy application" ([Reviewing OU Design Concepts](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/plan/reviewing-ou-design-concepts)). practitioners compress it: "organizational units are used to delegate admin rights and apply group policy settings, while groups are used to manage permissions" ([tenfold](https://www.tenfold-security.com/en/organizational-unit/)); "don't try to make OUs do the job of tagging multi-dimensional data like 'is in Sales dept and in London office' because that's what groups are for" ([Petri](https://petri.com/best-practices-for-designing-an-ad-ou-structure/)).

**why one OU, many groups.** an object's DN *is* its OU path. containment is the naming hierarchy — a tree by construction, so an object has exactly one parent. groups are a separate many-to-many relation layered on top via `member`. that's not an accident so much as X.500 inheritance: LDAP DNs are hierarchical names, and AD got its tree from the naming model, then got its DAG from a linked attribute.

**was the split a good idea? what practitioners say in hindsight.** the honest answer is: the *concept* (a tree for admin scope, a DAG for authz) is defensible; the *coupling* was the mistake. three things got welded to the OU tree that shouldn't share a structure:
1. delegation scope (ACL inheritance down the tree),
2. policy scope (GPO links),
3. the object's *name* (DN).

so moving a user to fix (1) changes (2) and (3). every seasoned AD person has a story about an OU reorg that silently re-applied a GPO or broke an app that cached a DN. the widespread "OU sprawl" complaint and the "flat and shallow" advice ([racknotes](https://racknotes.pro/active-directory-ou-design/), [Desmond/Richards *Active Directory* ch.13 on "collapsing the OU structure"](https://www.oreilly.com/library/view/active-directory-5th/9781449361211/ch13.html)) are practitioners trying to minimize how much the tree is used for anything. joe richards' bluntest take is that OUs aren't a security boundary at all: "a single forest cannot be isolated no matter how you try to break things up – staggering replication, OU security separation, whatever - it is still all connected" ([joeware 2009](http://blog.joeware.net/2009/03/11/1623/)). and some current GPO guidance goes further and says stop linking GPOs to OUs entirely — use item-level targeting and security filtering, keep OUs for delegation only ([industrialmonitordirect GPO design](https://industrialmonitordirect.com/blogs/knowledgebase/active-directory-gpo-design-baseline-and-item-level-targeting)) — which is, functionally, "make policy a group thing too."

**my read:** the split was right; the OU tree being *load-bearing for three unrelated things* was wrong. the correct modern move is: identity is flat, scopes are groups, policy targets are groups. you need the tree only if you need a *name* hierarchy, and you don't.

## 3. group scope and type

**type.** security vs distribution is a bit in `groupType` (0x80000000). distribution groups "aren't security enabled, so you can't include them in DACLs" ([Microsoft Learn security groups](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups)) — and crucially they don't go in the token, so they don't count toward token bloat. that's the only reason they exist as a separate type: to let Exchange have 10,000 mailing lists without putting 10,000 SIDs in anyone's PAC. the type is really "does membership in this thing get materialized into every auth decision."

**scope.** the Microsoft matrix, verbatim structure ([same page](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups)):

| scope | may contain | may be member of | grants on |
|---|---|---|---|
| universal | accounts, globals, universals from any domain in forest | universals; domain locals in forest or trusting forests | anywhere in forest/trusting forests |
| global | accounts + globals from *same domain only* | universals, globals (same domain), domain locals anywhere incl. trusting domains | anywhere |
| domain local | anything from anywhere incl. external forests, + other DLs from same domain | other DLs same domain; computer local groups same domain | *within the same domain only* |

conversion rules are the tell: global→universal only if not nested in another global; DL→universal only if it contains no other DL. the constraints are exactly "would this break the replication invariant."

**why it exists.** three replication scopes. global group membership is stored only in the home domain (not in PAS) — cheap to change, but other domains can't see inside it. universal membership is in the PAS — every GC in the forest sees it, so every change replicates forest-wide. domain local membership is also not in the PAS, *and* the group's SID is only honored by resources in its own domain, so it can safely contain foreign principals without that information ever needing to cross a domain. "changes to universal groups require forest-wide security rights inappropriate in most large enterprises" and "any change to a universal group triggers (potentially expensive) global catalog replication" — which is explicitly why universals couldn't just replace globals ([AGDLP, Wikipedia](https://en.wikipedia.org/wiki/AGDLP)).

**is it an accident of multi-domain forests?** yes, completely. in a single domain "the scope of groups will have no effect on performance" ([ss64](https://ss64.com/nt/syntax-groups.html)) and Microsoft's own RMS team says "you don't technically have to" ([RMS blog](https://learn.microsoft.com/en-us/archive/blogs/rmssupp/single-forest-single-domain-seeks-non-universal-group-to-share-many-bytes-of-rms-data-with)). the scope is a leaked implementation detail of 1999 WAN replication. do not copy it.

**AGDLP — the part that matters to you.** "Accounts → Global groups → Domain Local groups → Permissions." users go in global groups that *represent business roles*; permissions are granted to domain local groups that *represent a resource entitlement*; role groups are nested into resource groups ([Wikipedia AGDLP](https://en.wikipedia.org/wiki/AGDLP), [TechTarget](https://www.techtarget.com/searchwindowsserver/tip/Active-Directory-nesting-groups-strategy-and-implementation)). the operational rule: "add users to role groups only (not permission groups), except in tightly controlled break-glass scenarios" ([windows-active-directory.com RBAC](https://www.windows-active-directory.com/role-based-access-control-rbac-using-ad-groups.html)).

here's the thing practitioners say in hindsight that the textbooks don't: AGDLP was *sold* as a replication optimization, but the reason people still swear by it in single-domain shops has nothing to do with replication. it survived because the scope rules **physically enforce the direction of the edge.** "if all organisational groups are Global and resource groups are Domain Local then it is not possible to add group permissions the wrong way around" ([ss64](https://ss64.com/nt/syntax-groups.html)) — you cannot put a DL into a global. the type system makes "resource group nested inside role group" a compile error. and because a DL "can grant permissions within the same domain" only, the *resource* side is bound to where the resource lives, while the *role* side is portable.

so AGDLP encodes two distinct relations that AD otherwise can't tell apart:
- **containment**: "alice is in `Role-Finance`" (a fact about alice)
- **implication**: "`Role-Finance` ⇒ `Res-GL-ReadWrite`" (a fact about an entitlement policy)

both are stored as `member` edges. the *only* thing distinguishing them is the scope bits on the two endpoints. and in environments that don't enforce AGDLP, both relations collapse into an undifferentiated graph — which is the precise failure Trimarc describes: a department group `ITStaff` nested into `Domain Admins`, so hiring into the department grants domain admin, and then an MSP's group nested into `ITStaff` ([Trimarc](https://www.hub.trimarcsecurity.com/post/let-s-talk-about-nested-groups)). "fewer than 10 intended admins, almost 150 actual." that's containment-edges being used where an implication-edge was meant, with no type to stop it.

## 4. nested groups and transitive membership

**depth:** unlimited. **cycles:** allowed. AD refuses "a group cannot be made a member of itself" for the direct case and happily accepts A∈B, B∈C, C∈A ([Netwrix nested groups](https://oldblog.netwrix.com/2023/04/26/active-directory-nested-groups/), [rlmueller circular](https://www.rlmueller.net/CircularNested.htm)). AD's own closure computation doesn't loop (it's a fixpoint over SIDs). but a cycle *merges privilege sets* — A inherits everything B has and vice versa — and third-party recursive enumerators crash or spin ([Netwrix](https://oldblog.netwrix.com/2023/04/26/active-directory-nested-groups/)). the practitioner consensus is that cycles are always a mistake and always accidental; nobody defends them. your DAG constraint is correct.

**server-side closure, three ways:**
- `tokenGroups`: base-scope read on one object, returns SIDs. fastest; security groups only; needs GC.
- `LDAP_MATCHING_RULE_IN_CHAIN` (`1.2.840.113556.1.4.1941`): an extended-match in a *filter*, "walks the chain of ancestry... all the way to the root" ([Atlassian KB](https://support.atlassian.com/crowd/kb/active-directory-user-filter-does-not-search-nested-groups/)). built to replace client-side recursion. direction matters enormously: `(member:1941:=<userDN>)` over a groups OU is cheap; `(memberOf:1941:=<groupDN>)` over all users is a chain walk per candidate. Checkmk ripped it out as "incredibly slow" and wrote their own resolver ([Checkmk werk 6847](https://checkmk.com/werk/6847)); CloudBees and Zeppelin adopted it ([CloudBees](https://docs.cloudbees.com/docs/cloudbees-cd-kb/latest/cloudbees-cd-kb/kbec-00445-active-directory-provider-working-slow-with-big-ad-repositories), [Zeppelin PR](https://github.com/apache/zeppelin/pull/2062)). for cross-domain correctness "all security groups in the hierarchy must be Universal."
- `msDS-memberTransitive` / `msDS-memberOfTransitive`: DN-valued constructed transitive closure.

lesson: AD computes closure *on demand, per query*, with no cache. that works because DCs are fast and the graph is small per-user. what AD did *not* do is materialize the closure — and the cost shows up as the "incredibly slow" complaints and "we can't change SDProp frequency because LSASS overhead" caveats. **your `effective_memberships` materialization is the right call** for a 150-person directory: the write amplification is trivial and every read becomes an index lookup.

**token bloat.** the PAC's `KERB_VALIDATION_INFO` carries `GroupIds` (RIDs in the account domain), `ExtraSids` (full SIDs for groups in *other* domains and sIDHistory), and `ResourceGroupIds` (domain-local RIDs in the resource domain, added by the resource DC at service-ticket time) ([MS-PAC KERB_VALIDATION_INFO](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-pac/69e86ccc-85e3-41b9-b514-7d969cd0ed73)). Microsoft's sizing formula from KB 327825: `1200 + 40d + 8s` (d = domain-local + foreign + sIDHistory entries at 40 bytes, s = same-domain at 8). default `MaxTokenSize` was 12,000 bytes for a decade, 48,000 since Server 2012 — capped there, not 64K, because HTTP headers base64 the token and IIS's `MaxFieldLength` tops out at 64K ([Shane Cothran](https://learn.microsoft.com/en-us/archive/blogs/shanecothran/maxtokensize-and-kerberos-token-bloat), [woshub](https://woshub.com/kerberos-token-size-and-issues-of-its-growth/)). independently of bytes, the LSA access token holds max 1024 SIDs, ~9 reserved for logon-type SIDs, so **1015 groups** is a hard logon failure: "the user's security context accumulated too many security IDs" ([tenfold](https://www.tenfold-security.com/en/wiki/maxtokensize-problem/), [activedirectoryfaq](https://activedirectoryfaq.com/2018/10/ad-migration-maximum-number-of-group-memberships/)). nested groups count. sIDHistory counts at 40 bytes each. accounts "trusted for delegation" roughly double.

the deeper lesson isn't the number. it's that **AD pushes the full transitive closure into every ticket**, so group sprawl becomes a *transport* problem, and the fix (resource SID compression, 2012) was a wire-format hack. an IdP that mints per-app tokens should not put every group in every token — which is exactly what `app_groups` prevents.

**group sprawl.** the only published figure I found: a Varonis sample assessment with 14,427 groups for 8,580 users, 26% of groups empty ([Varonis sample report](https://info.varonis.com/hubfs/docs/DRA-sample.pdf)). 1.7 groups per human. nobody knows what most of them are for because AD has no "purpose" field and `managedBy` is informational. `description` is free text. there's no owner, no expiry, no "which app uses this."

## 5. delegation of control

**the model.** every object has a security descriptor with a DACL of ACEs. AD's twist is *object-specific* ACEs: an ACE can carry an `ObjectType` GUID (an attribute, a *property set*, an extended right, or a validated write) and an `InheritedObjectType` GUID (apply only to children of this class) ([AD PowerShell team on object-specific ACEs](https://learn.microsoft.com/it-it/archive/blogs/adpowershell/add-object-specific-aces-using-active-directory-powershell)). so "helpdesk may reset passwords on users in OU=Staff" is one inheritable ACE on the OU: `ExtendedRight`, `User-Force-Change-Password`, inherit to `user` objects. property sets are `controlAccessRight` objects that bundle attributes (e.g. "Personal Information", "Group Membership") so one ACE covers many attributes. validated writes are rights with server-side semantic checks — "Self-Membership" lets a principal add/remove *only itself* from `member`; "Validated write to DNS host name" constrains the value shape.

**the wizard** ([Delegation of Control](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/delegation-control-wizard)) is a template-driven ACE writer with 11 canned tasks ("Create, delete, and manage user accounts", "Modify the membership of a group", "Manage Group Policy links"...) stored in `delegwiz.inf`. it writes ACEs. it has **no undo**. there is no "list delegations" view anywhere in the product — you read effective ACLs object by object.

**"Manager can update membership list."** `managedBy` is a single-valued DN that "doesn't confer rights to manage the object." the checkbox adds an ACE granting `WriteProperty` on `member` (GUID `bf9679c0-0de6-11d0-a285-00aa003049e2`) to the managedBy principal ([Richard Siddaway](https://richardspowershellblog.wordpress.com/2013/11/04/manged-by-for-groups/), [bashlin35](https://medium.com/@bashlin35/delegating-manager-can-update-membership-list-2c91028b5034)). they aren't linked: change `managedBy` and the old manager keeps the ACE. and delegating the ability to tick the box requires `WriteDacl` on the group — so you can't safely delegate delegation.

**AdminSDHolder / SDProp.** `CN=AdminSDHolder,CN=System` holds a template security descriptor. every 60 minutes (registry `AdminSDProtectFrequency`, 60–7200s) the PDC emulator runs SDProp, which stamps that descriptor onto every member of the protected groups (Administrators, Domain Admins, Enterprise Admins, Schema Admins, Account/Server/Print/Backup Operators, Replicator, krbtgt, DCs, RODCs, Key Admins...), sets `adminCount=1`, and **disables ACL inheritance** on them ([Appendix C: Protected Accounts and Groups](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/plan/security-best-practices/appendix-c--protected-accounts-and-groups-in-active-directory)). it's a defense: a helpdesk delegate with "reset password on OU=Staff" must not be able to reset a domain admin who happens to live there. consequences: any delegation you set on a protected account vanishes within the hour with no event; once-protected accounts keep `adminCount=1` and broken inheritance forever after leaving the group (the "AdminSDHolder orphan" problem); and if an attacker writes an ACE to AdminSDHolder itself, SDProp faithfully propagates their backdoor to every admin every hour ([adsecurity #15](https://adsecurity.org/?p=1906)). it's a reconciliation loop fighting the inheritance model because the inheritance model has no notion of "this object is more sensitive than its container."

**what goes wrong.** the Black Hat 2017 paper that birthed BloodHound's ACL edges, "An ACE Up the Sleeve" ([SpecterOps PDF](https://specterops.io/wp-content/uploads/sites/3/2022/06/an_ace_up_the_sleeve.pdf)), lists the rights that compound: `GenericAll`, `WriteDacl`, `WriteOwner`, `WriteProperty` on `member`, `User-Force-Change-Password`, `DS-Replication-Get-Changes(-All)`. and why audit fails: inheritance layers, object-specific ACEs need schema knowledge to interpret, and "legacy permissions and delegated administrative rights accumulate over time." BloodHound exists because the only way to answer "who can become domain admin" is to load every ACE in the forest into a graph database and run shortest-path. **AD's delegation model is expressive at object granularity and has zero affordance for listing, auditing, or revoking what was delegated.** the primitives are a security descriptor language; nobody built the ledger on top.

## 6. how apps consume AD

**LDAP with a service account.** the app binds as `svc_whatever` and reads. what can it read? by default, everything. `Authenticated Users` is pre-populated into `Pre-Windows 2000 Compatible Access` even on a fresh Server 2025 forest, and that group has inherited read on all users and groups from the domain root ([Semperis](https://www.semperis.com/blog/security-risks-pre-windows-2000-compatibility-windows-2022/), [MS-ADTS Pre-Win2000 group](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/7a76a403-ed8d-4c39-adb7-a3255cab82c5)). even after removing it, "all your users can still read the memberships of all groups in your Active Directory forest." the data model has no concept of "this group is relevant to app X." so every integration has a `group_filter` config and reads `memberOf` — which, per §1, lies about primary group, nesting, and cross-domain.

**Kerberos PAC.** the app gets the full closure as SIDs and resolves names via LSA. accurate, bloated, and the app sees every group the user is in, including ones that are none of its business.

**ADFS claim rules.** a rule language: `c:[Type == windowsaccountname] => issue(store="Active Directory", types=("...Group"), query=";tokenGroups;{0}", param=c.Value)` dumps *every* group as a claim; "Send Group Membership as a Claim" emits one claim for one SID ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups), [when to use group membership claim](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups)); `memberOf` rules need regex rules to strip DNs to CNs and "will leave out any domain local groups" via tokenGroups because "there is no intuitive way to answer which domain to pull these from" ([TechNet wiki](https://learn.microsoft.com/en-us/archive/technet-wiki/13829.ad-fs-2-0-domain-local-groups-in-a-claim), [moorereason: swamp of claims rules](https://moorereason.wordpress.com/2013/10/08/the-swamp-of-adfs-claims-rules/)). ADFS is the closest AD ever got to your `app_groups` — a per-relying-party mapping of group → claim — and it was implemented as a per-app *script* over the whole directory rather than as a *relation* in the directory.

**Entra Connect / Cloud Sync.** forward sync flattens nothing (nested groups sync as nested); primary group is dropped; writeback of cloud security groups to AD was deprecated in Connect Sync (June 2024) and reborn in Cloud Sync, where written-back groups are always universal, "nested groups are not synchronized," and cloud-only members are dropped ([group writeback](https://learn.microsoft.com/en-us/entra/identity/hybrid/group-writeback-cloud-sync), [migrate GWB](https://learn.microsoft.com/en-us/entra/identity/hybrid/cloud-sync/migrate-group-writeback)). the sync layer has to pick one scope because scope is a leaked detail that the cloud model (rightly) doesn't have.

**who controls what an app sees:** nobody. the bind account's ACLs, which are "everything" by default. there's no object in the directory that says "app X may learn that `Role-Finance` exists." that absence is the hole.

## 7. multi-population

AD's answer to "different populations" is **more directories**: child domains (shared schema+config, separate NC, transitive trust), separate forests (separate schema, explicit trust), and `foreignSecurityPrincipal` stubs — objects in `CN=ForeignSecurityPrincipals` with only an `objectSid`, created on demand when you add an external principal to a domain-local group, so that `member` has a DN to point to ([SpecterOps trusts guide](https://specterops.io/blog/2017/10/30/a-guide-to-attacking-domain-trusts/)). the account forest / resource forest pattern put people in one forest and servers in another; ESAE/"red forest" put *admins* in a third hardened forest. Microsoft retired ESAE in 2020–21 as "not practical for most organizations" ([JumpCloud on ESAE](https://jumpcloud.com/it-index/what-is-a-red-forest-enhanced-security-administrative-environment-esae), [Security Magazine](https://www.securitymagazine.com/articles/96167-red-forest-is-gone-now-what)).

Entra's two answers are instructive: **B2B guests** are stub objects in *your* tenant pointing to an identity in *their* tenant (that's a foreignSecurityPrincipal with a nicer coat), and **External ID / CIAM** is "a separate tenant... purpose-built for external audiences... to keep customer and internal identity management cleanly isolated" ([Entra External ID overview](https://learn.microsoft.com/en-us/entra/external-id/external-identities-overview)). Microsoft, with 25 years of hindsight, chose *separate directory* for the 50k-community case.

**what AD would say about your 50k:** it would agree with you, loudly. every AD design doc treats populations with different admin, policy, and trust boundaries as separate domains or forests, and the whole token/PAC/replication machinery assumes the directory is the *workforce*. putting 50k consumers in the same group graph as 150 staff means every closure computation, every audit, every `app_groups` decision has to exclude them. keep them out. if some community member ever needs a staff-style entitlement, do what AD does: mint a stub (foreign principal) in the staff directory that references the external identity, and let *that* be a group member.

## 8. what AD got RIGHT

- **linked attributes with automatic back-links.** one write, two readable directions, referential integrity for free, and (with LVR) per-edge replication. every modern system that stores `members[]` on the group *and* `groups[]` on the user and reconciles them in app code is reinventing this worse.
- **server-computed transitive closure** (`tokenGroups`, `1941`). the directory owns the semantics of "is a member"; clients don't each write a buggy recursive walk.
- **SIDs: stable, opaque, immutable, never reused, separate from names.** rename anyone, move anything, ACLs don't care. the entire `objectGUID` vs DN story is the same point: "because an object's distinguished name changes if the object is renamed or moved, the distinguished name is not a reliable identifier" ([Object Names and Identities](https://learn.microsoft.com/en-us/windows/win32/ad/object-names-and-identities)).
- **sIDHistory.** a principled way to say "this identity *was* that identity" so references survive migration. almost nothing else has this.
- **one extensible schema**, forest-wide, with typed syntaxes, link semantics, PAS flags, and indexing flags on each attribute.
- **delegation that's at least possible at attribute granularity** with class-scoped inheritance and semantically-validated writes (self-membership). the *expressiveness* is excellent.
- **a replication model** with per-attribute (and per-link-value) metadata, USNs, and conflict resolution — SpecterOps literally hunts attackers using replication metadata ([SpecterOps](https://specterops.io/blog/2017/09/06/hunting-with-active-directory-replication-metadata/)).
- **everything is an object with a GUID**, including groups, OUs, GPOs, trusts, and the schema itself.

## 9. what AD got WRONG

- **OU/group split with the OU tree carrying name + policy + delegation.** three concerns, one structure; moves are scary; people duplicate org structure in both OUs and groups.
- **group scope as a user-visible type.** a 1999 WAN replication strategy exposed as a required decision on every group, with conversion rules and nesting errors, meaningless in a single domain.
- **two membership encodings** (`member` and `primaryGroupID`). permanently breaks `memberOf`, Entra Connect, SharePoint sync, every LDAP app.
- **memberOf lies**: primary group, nesting, cross-domain, cross-forest, and depends on which port you asked.
- **ACLs nobody can read.** no delegation ledger; SDProp as a reconciliation loop against the inheritance model; `managedBy` decoupled from its own ACE; "An ACE Up the Sleeve" and BloodHound as the consequence.
- **token bloat.** full closure in every ticket, byte limits, a 1015 hard cap, resource SID compression as a wire hack.
- **no notion of "which apps may see this group."** read-everything by default; group→claim mapping outsourced to ADFS scripts and app-side filters.
- **DNs as identifiers** that change on move, with every integration tempted to store them anyway.
- **cycles allowed**, no depth limit, no purpose/owner/expiry on groups → sprawl with no metadata to prune by.
- **containment and implication indistinguishable** except by the accident of AGDLP discipline.

## 10. rebuilding AD's group model for one small org in 2026

measured against your draft: `groups`, `memberships` (person-or-group → group, DAG), `grants` (grantee_group, permission, target_group, recursive?), materialized `effective_memberships`, `app_groups` (app, group, claim_name, required?).

**keep from AD:**
- opaque immutable ids on every row. never let a name or path be a foreign key. (you're presumably doing this; AD's whole DN saga says make it a rule.)
- one write for an edge, both directions derivable. your `memberships` table *is* the forward link; `effective_memberships` is a materialized back-link-plus-closure. good. make sure the closure is recomputed transactionally on membership writes, and consider storing `(ancestor, descendant, depth, via_path_count)` so removals are incremental instead of full rebuilds.
- server-computed closure as the *only* membership API. no consumer should ever see direct edges unless it's the admin UI.
- a "security-enabled" distinction — not as AD's type bit, but as: does this group participate in `app_groups`/`grants` at all, or is it purely organizational? AD's distribution group was a token-size hack, but the underlying insight (not everything called a group should be an authz group) is sound.
- `sIDHistory`'s idea: when you merge or re-key a person (contractor → staff, duplicate cleanup), keep a `previous_ids` so references in apps survive.

**drop:**
- scope. obviously.
- OUs. your model has no tree and that's correct. delegation scope should be a group, policy target should be a group.
- primary group. one encoding of membership. ever.
- cycles. you've banned them. also add a depth cap (AD practitioners say "enforce a maximum nesting depth" — 3 or 4 is plenty for 150 people) and make the UI show the path, not just the fact.

**does `grants` with `recursive` replace OU-inherited ACLs?** mostly yes, and it's *better* than AD's model in the way that matters: a grant is a row in a table you can `SELECT * FROM`, which is the ledger AD never had. BloodHound is a 10-year industry because this table didn't exist. but three gaps vs. AD's ACL model, and you should decide deliberately about each:

1. **the AdminSDHolder problem will come for you.** "recursive grant on `Staff` ⇒ manage membership of everything under `Staff`" will, the day someone nests `Admins` under `Staff` for convenience, give the helpdesk the ability to add themselves to `Admins`. AD's answer was a cron job that fights inheritance. yours should be structural: a `protected` flag on groups that makes them *ineligible as targets of recursive grants* (only direct grants reach them), checked at grant evaluation time, not reconciled later. that's SDProp without the hourly race.
2. **AD's permission vocabulary is semantically validated** — "Self-Membership" (add/remove only yourself), "write member" vs "write all". your `permission` column should include at least: `read_membership`, `manage_membership`, `manage_grants` (delegate delegation — AD's `WriteDacl`, the dangerous one), `manage_group` (rename/delete), `join_self`/`leave_self`. keep `manage_grants` off recursive grants by default. the ability to *delegate* is the thing that escalates.
3. **implication vs containment.** `recursive` on a grant is "scope inheritance" (AD's `InheritedObjectType`); it's unrelated to membership implication. but your `memberships` table conflates the two things AGDLP separates. see below.

**does `app_groups` solve "apps read everything"?** yes, and it's the single biggest improvement over AD in your draft. it's the relation ADFS tried to express as per-RP claim-rule scripts and Entra expresses as app role assignments. two refinements AD's history argues for: (a) make it the *only* read path — no "list groups" endpoint for apps, the token/userinfo for app X contains exactly `claim_name` for groups in `app_groups` where user ∈ `effective_memberships`. (b) `required?` is doing the work of ADFS "issuance authorization rules" — fine, but note AD-land learned that "must be in group G to sign in" and "emit G as claim" are different concerns that end up on different lifecycles (security team owns one, app team owns the other). consider whether `required` should be its own tiny table so revoking access doesn't mean touching claim config. also: the thing AD consumers hit constantly is "which groups does app X actually care about" being unknowable; `app_groups` answers it in one query. that's the win. don't dilute it with a wildcard.

**is single-edge-type nesting equivalent to AGDLP, or does the role/resource split buy something real?** it buys something real, and your model currently doesn't have it. AGDLP's two tiers are **containment** ("alice ∈ Role-Finance" — a fact about alice, changes when HR changes) and **implication** ("Role-Finance ⇒ GL-ReadWrite" — a fact about policy, changes when an app owner decides). in AD both are `member` edges and the only guard is scope bits. the Trimarc 10-vs-150-admins story is exactly what happens when an implication edge gets created where a containment edge was intended and nothing in the type system objects.

in your model the implication relation already has a natural home: **`app_groups` is the resource tier.** an `app_groups` row *is* "this group ⇒ this entitlement in this app." so you don't need AD's second group kind — you need to decide where role→role nesting is allowed. options, in increasing strictness:

- **(loose)** keep one edge type, DAG, depth cap, and lint for "a group that appears in `app_groups` or as a `grants` target has nested *parents*." that catches "someone nested `All-Staff` into `Prod-Deployers`."
- **(medium)** add a `kind ∈ {role, entitlement}` column on `groups`. people and roles may be members of roles; roles may be members of entitlements; entitlements may not be members of anything; only entitlements may appear in `app_groups`; `grants` targets may be either. this is AGDLP with the scope nonsense removed and the actually-useful invariant kept: **the edge direction is enforced by type, not by discipline.** it's one column and three check constraints.
- **(strict)** two tables, `memberships` (person|role → role) and `entitlement_rules` (role → entitlement). cleanest semantics, costs you the uniform closure query.

my opinion: do medium. the whole lesson of §3 is that AGDLP survived in single-domain shops *despite* having no replication reason, because the type constraint on nesting direction prevents the most common catastrophic mistake. you get that for one nullable-free column. and it makes `app_groups` honest: it should only ever point at entitlement-kind groups, which means "what does app X see" is "the entitlements it's been bound to," never a role or a department by accident.

one last thing to steal, from the thing AD got most wrong: give groups metadata AD never had — `owner` (a group, not a person; and unlike `managedBy`, make it *mean* something by auto-granting `manage_membership`), `purpose`, `expires_at`, `created_by`. 26% empty groups happens when the directory can't tell you why a group exists.

---

the thesis in one line: AD's primitives (linked attributes, SIDs, server-side closure, object-level delegation, a single schema) are better than most of what replaced them; its *compositions* (the OU tree carrying three concerns, scope as type, two membership encodings, ACLs with no ledger, full closure in every ticket, no app-visibility relation) are the lessons. your draft already avoids most of the compositions. add a `kind` to groups so the AGDLP direction is enforced by type, a `protected` flag so recursive grants can't reach admin groups, and a real permission vocabulary with `manage_grants` kept off the recursive path — and you'll have kept what was good and dropped what wasn't.
